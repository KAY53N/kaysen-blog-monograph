## 0x00 应用介绍

Redis 是开源的 Key-Value 数据库，用 ANSI C 写，支持网络，数据可以放内存也可以持久化，并提供多种语言的 API。

## 0x01 漏洞介绍

这不是 Redis 协议本身的远程代码执行，而是**默认配置被改错、又暴露到不可信网络**之后的未授权访问。常见组合是：

- 监听 `0.0.0.0:6379`（或其它公网可达地址），而不是只绑 `127.0.0.1`
- 没有 `requirepass`，空口令或弱口令
- 关掉了 `protected-mode`
- 进程用 root 跑
- 6379 没有防火墙 / 安全组限制

默认安装一般是只允许本地访问。一旦改成对公网开放、又不设认证，任何人连上都能执行 Redis 命令：读数据、删数据、改配置、触发持久化。历史上这类暴露实例常被拿去写文件、种挖矿（当时常见的有 yam2 minerd、watch-smartd 一类），或者把数据删掉、加密勒索。

危害来自「能对 Redis 下命令」，具体能做到哪一步，取决于进程权限、文件系统写得动哪里、机器上还开了什么服务。把利用步骤写成教程，等于给别人现成的入侵路径，这里不写。

## 0x02 自查

查的是**自己的**实例，不要拿扫描器和爆破工具对着别人的地址试。

1. 进程监听地址是不是只有本地。`bind 127.0.0.1` 才是只给本机用；绑了 `0.0.0.0` 或其它网卡，就要假设这个端口能被同网段或公网摸到。
2. 有没有 `requirepass`，口令够不够复杂。空口令等于没门。
3. `protected-mode` 是否开启。保护模式会在未绑定且无密码时拒绝外网客户端。
4. 安全组、防火墙有没有把 6379 从公网挡掉，是否只放行白名单。
5. 进程是否用非 root 账号跑。用 root 跑，一旦被未授权访问，能写的路径会宽很多。
6. 本机用 `redis-cli` 连自己的实例，确认未授权客户端什么都做不了。

端口对外开放、又能无口令连上，就可以读到实例里的数据。这已经是事故，不必再往下「验证危害」。

## 0x03 不要做的事

下面这些不属于博客该复制的内容，这里明确不写：

- 对公网 Redis 做密码爆破
- 往实例里写 SSH 公钥、改持久化路径、拿到系统登录权限
- 真实 IP、口令、登录成功的终端记录

对不属于你的系统做这些，在大多数地方都违法。应急时如果已经确认是自己的机器被打开了，应先断公网、改口令、查持久化目录和 `~/.ssh`、查异常进程，而不是复现攻击。

## 0x04 修复建议

1. **限制访问来源。** `bind` 只绑需要的地址；安全组 / 防火墙只放行白名单。公网不要直接暴露 6379。
2. **设复杂口令，改掉默认端口只是辅助，不能代替口令。** 打开 `requirepass`，口令按密钥来管，不要用生日、主机名这类弱口令。
3. **不要用 root 跑 Redis。** 单独账号、最小写权限。
4. **关掉危险配置。** 生产环境谨慎对待 `CONFIG` 命令，能 rename/disable 的就禁用；持久化目录不要放在敏感路径下。
5. **SSH 本身也要加固。** 禁止 root 直接登录，密钥文件权限收紧，能关密码登录就关。

SSH 配置可以参考（按你的发行版调整后重启 sshd）：

```
PermitRootLogin no
PasswordAuthentication no
AuthorizedKeysFile .ssh/authorized_keys
ChallengeResponseAuthentication no
```

Redis 侧最小集：

```
bind 127.0.0.1
protected-mode yes
requirepass <足够长的随机口令>
```

需要给别的机器访问时，走内网、VPN 或 SSH 隧道，而不是把 6379 挂到 0.0.0.0。

## 0x05 总结

根因是远程可访问，同时又是空口令或弱口令。实例一旦暴露，数据读取、删除、勒索、挖矿都可能发生。修的是监听范围、认证、权限和防火墙，不是再准备一套「打进去」的命令。
